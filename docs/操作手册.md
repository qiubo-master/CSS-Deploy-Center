# ForgeOps CI/CD 中台操作手册

## 1. 使用范围

ForgeOps 用于统一管理项目、阿里云/其他云服务器/AutoDL、Docker 资源、GitHub Actions 流水线、版本发布和回滚。标准流程是：

1. 接入服务器并确认资源监控在线。
2. 准备 GitHub 代码仓库与容器构建文件。
3. 在“资源接入与一键部署”中登记项目、仓库和部署目标。
4. 配置仓库生产环境 Secrets。
5. 下发资源并执行首次部署。
6. 后续代码推送后使用“发布最新版本”。
7. 在流水线列表观察每个 GitHub Actions 步骤。

## 2. 角色与安全规则

- 控制台管理员令牌仅授权发布、回滚、服务器和项目登记，不是 GitHub Token。
- GitHub Token 保存在控制中心服务器 `/opt/css-deploy-center/shared/.env`，不得提交到仓库。
- SSH 私钥只保存在 GitHub Environment Secrets 或受控服务器目录，禁止写入代码、README 和聊天。
- 业务 `.env` 保存在目标服务器项目的 `shared/.env`，发布时复用。
- PostgreSQL、MySQL、Redis 等数据库端口不得直接开放公网。
- 监控代理必须通过 Docker 内网、云内网、VPN、HTTPS 网关或 SSH 隧道访问。
- 生产环境建议仅开放 `22`、`80`、`443` 和明确需要的业务端口。

## 3. 第一步：接入云服务器

### 3.1 接入前检查

目标服务器需要满足：

- Linux，推荐 Ubuntu 22.04 或更新版本。
- 可通过 SSH 登录，推荐使用独立部署密钥。
- 已安装 Docker Engine 与 `docker compose` 插件。
- 已安装 Python 3，用于只读资源监控代理。
- 根磁盘建议至少保留 10GB。
- 服务器时间同步正常。
- 控制中心能够通过内网、SSH 隧道或安全地址访问监控代理。

检查命令：

```bash
docker --version
docker compose version
python3 --version
df -h /
free -h
```

### 3.2 在控制台登记服务器

1. 打开 CI/CD 控制台。
2. 进入“云服务器与 AutoDL 资源监控”。
3. 点击“＋ 接入服务器”。
4. 填写服务器 ID，只能使用小写字母、数字和连字符，例如 `aliyun-prod-2`。
5. 填写显示名称、服务商、区域和服务器地址。
6. 选择类型：云服务器、AutoDL 或裸金属。
7. 选择允许部署到该服务器的项目。
8. 填写监控地址和独立监控令牌。
9. 输入管理员令牌并保存。

### 3.3 安装资源监控代理

仓库提供 `ops/resource-agent.py`。代理采集：

- 主机 CPU 核数和使用率；
- 总内存、已用内存；
- 根磁盘容量和使用量；
- NVIDIA GPU 使用率和显存（存在 `nvidia-smi` 时）；
- Docker 容器、Compose 项目标记、容器 CPU 和内存。

代理必须配置独立随机令牌：

```bash
sudo install -m 750 ops/resource-agent.py /usr/local/bin/forgeops-resource-agent
sudo env \
  FORGEOPS_MONITOR_TOKEN='独立随机令牌' \
  FORGEOPS_MONITOR_PORT=9108 \
  FORGEOPS_MONITOR_BIND=127.0.0.1 \
  /usr/local/bin/forgeops-resource-agent
```

生产环境使用 systemd 运行。与控制中心不在同一服务器时，推荐建立 SSH 隧道，禁止直接将 `9108` 暴露公网。

### 3.4 AutoDL 特别说明

1. AutoDL 实例必须处于“运行中”。
2. 每次开关机后确认公网 SSH 主机名和端口是否变化。
3. AutoDL 代理监听 `127.0.0.1:9108`。
4. 由主阿里云服务器使用独立 SSH 密钥建立持久端口转发。
5. systemd 不可用的 AutoDL 环境可使用平台的开机自启动脚本启动代理和隧道。
6. GPU 数据依赖 `nvidia-smi`。

### 3.5 验收标准

服务器卡片必须满足：

- 状态为“在线”；
- 显示真实 CPU、内存和磁盘；
- GPU 服务器显示 GPU/显存；
- 显示 Docker 项目和容器占用；
- 容量结论为“可下发”或明确说明不足原因。

容量策略默认额外保留 20% CPU、20% 内存和 5GB 磁盘。监控离线时禁止首次资源下发。

## 4. 第二步：准备 GitHub 代码仓库

仓库至少需要：

- 一个默认分支，通常为 `main`；
- 至少一个提交，空仓库无法创建 Actions 工作流；
- `Dockerfile`，或 `docker-compose.yml`/`compose.yml`；
- `.env.example`，只包含变量名和安全示例；
- 健康检查接口，推荐 `/api/health`；
- 不提交 `.env`、密码、API Key 和 SSH 私钥。

控制中心 GitHub Fine-grained Token 权限：

- Actions: Read and write
- Contents: Read and write（自动建立流水线时需要）
- Metadata: Read

## 5. 第三步：填写仓库和资源配置

1. 打开“资源接入与一键部署”。
2. 填写项目 ID，例如 `ai-ops`。
3. 填写项目名称。
4. 填写完整 GitHub 地址，例如 `https://github.com/qiubo-master/AI_OPS`。
5. 填写分支，通常为 `main`。
6. 选择已经在线的部署服务器。
7. 流水线文件默认使用 `deploy.yml`。
8. 填写预期访问地址和健康检查 URL。
9. 勾选“自动创建标准 deploy.yml”。
10. 输入管理员令牌。
11. 点击“检查并建立部署流水线”。

系统会检查：

- 仓库是否存在且 Token 有权访问；
- 分支是否存在；
- Dockerfile 是否存在；
- Compose 文件是否存在；
- `.github/workflows/deploy.yml` 是否存在；
- 目标服务器是否登记；
- 项目与服务器是否绑定。

如果仓库非空但没有流水线，系统通过 GitHub Contents API 自动创建标准工作流。如果仓库为空，先推送项目代码，再重新执行。

## 6. 第四步：配置仓库生产 Secrets

进入目标仓库：`Settings → Environments → production`，配置：

- `DEPLOY_HOST`：目标服务器地址；
- `DEPLOY_PORT`：SSH 端口，通常为 `22`；
- `DEPLOY_USER`：部署用户；
- `DEPLOY_SSH_KEY`：完整私钥；
- `DEPLOY_HOST_KEY`：通过 `ssh-keyscan` 获取的主机公钥。

主机公钥示例：

```bash
ssh-keyscan -T 10 -p 22 -t ed25519,rsa your-server-ip
```

私钥对应的公钥必须写入目标服务器：

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
echo 'ssh-ed25519 AAAA...' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

## 7. 一键资源下发与首次发布

1. 选择项目。
2. 展开“首次部署与资源调整”。
3. 选择目标服务器。
4. 选择轻量、标准或增强资源档位。
5. 选择公网独立端口或统一 Nginx 网关。
6. 填写宿主机端口。
7. 确认服务器状态为在线且容量判断通过。
8. 输入管理员令牌。
9. 点击“下发资源并部署”。

流水线将依次执行代码检出、仓库校验、SSH 配置、制品打包、上传、Docker 构建、容器启动和版本激活。

首次发布前，在目标服务器准备业务环境文件：

```bash
sudo mkdir -p /opt/forgeops/项目仓库名/shared
sudo editor /opt/forgeops/项目仓库名/shared/.env
sudo chmod 600 /opt/forgeops/项目仓库名/shared/.env
```

## 8. 日常版本发布

1. 开发人员将代码推送到项目主分支。
2. 打开控制台并选择项目。
3. 确认“GitHub 最新版本”和“线上版本”不同。
4. 输入管理员令牌。
5. 点击“发布最新版本”。
6. 在“最新流水线实时阶段”观察每个 Job/Step。
7. 流水线成功后访问业务地址和健康检查地址。

页面每 12 秒同步一次 GitHub Actions。流水线列表展示版本、状态、触发方式、执行人、开始时间和耗时；“详情”可打开 GitHub 完整日志。

## 9. 回滚

1. 选择需要恢复的项目。
2. 输入管理员令牌。
3. 点击“回滚上一版本”。
4. 观察回滚流水线。
5. 验证健康检查和核心业务功能。

应用版本回滚不代表数据库自动回滚。涉及数据库结构的发布必须提供向后兼容迁移和单独的数据恢复方案。

## 10. 常见故障

### 服务器显示“待接入监控”

- 没有填写监控 URL；
- 代理未启动；
- 令牌不一致；
- SSH 隧道未运行；
- 防火墙或安全组阻断。

### 服务器显示“离线”

检查代理和隧道：

```bash
systemctl status forgeops-resource-agent
systemctl status forgeops-目标名称-tunnel
journalctl -u forgeops-resource-agent -n 100 --no-pager
```

### 仓库检查失败

- 仓库地址不正确；
- Fine-grained Token 未授权该仓库；
- 仓库为空；
- 默认分支不是 `main`；
- Contents 权限不是 Read and write。

### 流水线没有启动

- Actions 权限不是 Read and write；
- `deploy.yml` 文件名不匹配；
- 工作流不包含 `workflow_dispatch`；
- 分支不存在。

### SSH 上传超时

- 目标服务器安全组未开放 SSH；
- SSH 端口填写错误；
- GitHub Runner 网络临时波动；
- `DEPLOY_HOST_KEY` 与服务器当前主机公钥不一致。

### 发布成功但服务打不开

- 业务端口未开放；
- 容器未通过健康检查；
- `.env` 缺少变量；
- Nginx 反向代理地址错误；
- 应用实际监听端口与 Docker 映射不一致。

## 11. 上线验收清单

- [ ] 服务器监控在线。
- [ ] CPU、内存、磁盘数据正常。
- [ ] 项目与目标服务器绑定正确。
- [ ] 仓库非空且具备 Docker 构建文件。
- [ ] `deploy.yml` 可被手动触发。
- [ ] production Secrets 全部配置。
- [ ] 业务 `.env` 仅存在服务器。
- [ ] 首次下发容量判断通过。
- [ ] 流水线全部步骤成功。
- [ ] 健康检查返回成功。
- [ ] 业务页面可访问。
- [ ] 回滚流程至少演练一次。
